PR #27 was then owner-merged into `experiment/native-ios-audio` as `58698938`. Prior owner reports after N3c also documented an audible first launch and **real same-round task-switch recovery**, plus two fresh iPhone launches with **YouTube Picture-in-Picture already playing**. The first PiP start had initial `preload feed-peg stale` but succeeded after an explicit second preparation; the second PiP start had accepted activation and all sound preloads on the first attempt. Both PiP final reports retained 80 scheduled gameplay events, **0 software dispatches >=120ms** (1–3ms usual), `foregroundEpoch=0` (PiP competitor, **not** a task switch), `pending=false`. No evidence identifies what invalidated the first peg preload; the earlier one totally silent N3b post-build launch remains a historical open reliability observation. N3c's first-tap OS acceptance and Copy Audio Timing Report must remain available.

The approved roadmap calls for migrating **Feeding game modes** in N4. This PR limits that work to **Melody gameplay** because its **29 fixed MIDI 55…83 triangle PCM buffers and six native voices** already exist and were independently listened to in N3d. The entire ball/tune/clock/catch-percent system remains the original JavaScript activity owner.

## Native-only Melody behavior

1. **Explicit Got It! preparation, not app launch:** In `daily_questions_feed_game.js` only when `window.BibloZooNativeOnlyOutput.enabled === true`, mode is `melody` and Capacitor reports native iOS, the game's ordinary control choice → instructions → **Got It!** sequence routes to the existing `BibloZooFeedingNativeAudioPilot`. Native-only Melody now has its own visible preparation status and native-only sound badge, without a confusing Classic checkbox. The pilot calls `activateFromGesture({purpose:"feeding"})` then **only** `preload({soundId:"feed-melody"})`; Classic still prepares the separate `feed-star`, `feed-chomp`, `feed-peg` ID list. **No Web `AudioContext` or HTMLAudioElement is allocated for native Melody**. Other iOS modes not yet migrated remain explicitly native-only/silent under N1, not secretly Web-backed.
2. **Failure can't start a silent round:** Existing N3c guard waits for native preparation to succeed **before `startRound()`**. If the first tap is blocked, canceled, or times out, leave Instructions visible and enable **Try Again** with a sanitized reason, manual **DEV → Copy Audio Timing Report** hint and working Back. Another *human* tap retries. No automatic native output or Web fallback and no catch/reward credit for a round never started. A successful `prepared` is software readiness, **not** a guarantee the speaker emits audio; report any physically silent start despite `prepared`.
3. **Catch-note output, unchanged score:** The existing `catchMelodyNote` still increments caught/classified counts, updates percent, shows the same feedback and calls `playMelodyTone(runtime,entry.midi)` at the original catch. In native-only Melody, `playMelodyTone` now checks the mode, nonpaused state, native ready pilot and exact MIDI integer **55–83**, then issues one `play({soundId:"feed-melody",midi,volume:0.25,...})` via the already prewarmed native bank. The Swift worker schedules a triangle buffer; no oscillator/no browser fallback on native iOS, even if native play fails. Browser/PWA/Android and the original app retain the original 220ms Web triangle oscillator. The tune list, rest positions, onset/catch timeline, ball movement, steering/tilt/drag, scoring math, progress/rewards, result overlay and tune completion have **not** been modified.
4. **Same frozen round after a real app switch:** Existing `pauseFeedingGame` stops all sounds, freezes the game frame and Melody clock (`melody.pausedAt`), shows Welcome Back, and does not start Zoo Escape as an audio-error repair in native-only paths. The existing native **Let's go! / Resume** tap reactivates and preloads **just `feed-melody`**, then calls `continueFeedingAfterGesture` to shift paused deadlines and rebase the **same original Melody timeline**. No sound or score advances automatically on app foreground; Back exits. If native preparation fails, preserve the paused round and show genuine **Try again!**. The busy status never masquerades as an error. A stale promise after a second hide/exit is ignored by the existing activity generation and worker epoch checks.
5. **Resource safety:** N3a/b/c/d AVAudioSession .soloAmbient owner, six-voice Melody bank, bounded overlapping voices, 80-event native timing ring, 18-event first-tap/preflight history, no-WebKit-output guard, real interruption/route/media-reset teardown and privacy stay in place. Classically migrated native star/chomp/peg behavior is unchanged; no new native Swift synthesis in this PR. `backend=avengine-melody` in manual DEV timing rows means native `scheduleBuffer()` accepted, **not independently measured audible speaker onset**.

In Xcode choose **BibloZoo Audio Test** and run on a **real iPhone**. Linux GitHub CI and source/VM tests cannot compile AVFAudio or hear an output waveform.

1. **Melody actual gameplay, first fresh launch:** Choose Feeding **Melody** (Daily To-Do Preview or actual Feeding game), choose a tune and steering style, tap **Got It!**. Check that the native status progresses to “Melody notes prepared,” game starts and each **caught** colored musical snack plays a **distinct short pitched note**. This is now a *real Melody catch*, not the DEV E4 preview. Does the tune sound pleasant and at a reasonable level? Try multiple tunes, including the high and low parts. Compare to the unchanged original/Web app only in its separate installation. Ensure a **miss** never plays an invented catch note. Keep catch percentage, movement, tilt/drag and result/Back correct.
2. **Task-switch same-song Resume:** Mid-song after some catches, note tune/percent and switch to a YouTube/Facebook video or another app. Return. **No notes should play by themselves**; original game should remain frozen behind Welcome Back. Tap **Let's go!** once; native Melody preloads again and **the same song and percentage** resume at the correct next note without starting over, double rewards or skipping ahead. Confirm Back works from Welcome Back. Repeat if convenient. If a preflight refuses while paused, **Try again!** must remain available without playing Web output.
3. **First-tap errors / diagnostics:** If Melody's first Got It! fails, no silent known-bad game should start: same Instructions + **Try Again**, reason, Back. Try an explicit later tap; no background retries. **If audio is silent, delayed, or a note fails, do not restart yet**—tap DEV **Copy Audio Timing Report** and paste the entire timing plus **Native first-tap preflight** section. Look for `gesture | session | os-accepted/not-needed`, `preload | feed-melody | prepared/stale/error` and `feed-melody | scheduled | ... | avengine-melody`. Say clearly what was *actually heard*. Never interpret `scheduled` as speaker audibility.
4. **Preserve Classic:** Play native-only **Classic Feeding**, with smooth ball animations, peg beeps, chomp/star sounds close to collisions, task-switch Resume and correct first-tap Try Again as before. The DEV single E4 button should still be audible. Native Melody must not silently preload its bank during Classic. Nothing should play after Back/exit.
5. **Other modes and platforms:** Native Labyrinth/Bounce remain temporarily missing their dedicated unmigrated tones. Web/PWA/Android Melody should sound and behave as before. Original stable app and saved pet/verse/reward/recording/mic data must be untouched, no recording prompt, automatic sound, Web Audio fallback or Zoo Escape emergency game.

**Acceptance gate:** After merge, owner explicitly confirms **audible notes during actual Melody catches**, accurate song/catch percent and unchanged gameplay, same-song Resume with sounds and no auto-play, still-working Classic, and no Xcode compile error.
