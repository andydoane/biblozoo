# N7m — Read My Verse: external YouTube PiP / AirPods / Apple Music Play must trigger Welcome Back

**Owner reproduction (2026-11-11, America/Detroit):** In the **Keyboard Read My Verse** activity, with YouTube in **paused Picture-in-Picture** and BibloZoo foreground, tapping **Play** in the PiP player starts the external video but BibloZoo does not pause or show the fixed **Welcome Back / Let's go!** recovery; its own audio goes silent and tapping the app does not recover it. Similarly, while in BibloZoo, pressing **Play on AirPods** starts an Apple Music MP3, silences BibloZoo without a recovery popup or successful ordinary tap. Owner suspects other Read My Verse activities share the defect. This is specifically **external audio stealing the foreground session without an app task switch**, not a paused PiP or ordinary clip end.

## Verified source-level diagnosis

The Read-specific Swift `BibloZooNativeReadOutputPlugin` in `ios/App/App/SceneDelegate.swift` already observes **`AVAudioSession.interruptionNotification` `.began`**, genuine route changes and media-services loss/reset; it cancels native `clips` and `cues`, but sends a per-player `biblozooReadOutput(kind:"interrupted")` event **only when a clip exists**. It emits separate `biblozooReadLifecycle(phase:"willResignActive")` only when UIKit leaves the active state. In foreground **Keyboard/Typewriter/Order/Unscramble quiet turns** and **Balloons/Fish/Verse Crawl visual stages**, there can be **zero native AVAudioPlayer instances** while the Read activity and its clocks remain live; an AirPods/YouTube PiP takeover can deliver a genuine iOS audio interruption while **`UIApplication.shared.applicationState == .active`** and **`document.hidden === false`**, so neither previous signal reaches `pauseReadForInterruption`. JS keeps the activity running and holds a stale native activation token. An ordinary click does not constitute the deliberate recovery handshake.

## Focused changes — native-only, no new audio/recording engine

1. **Signal native OS interruption independent of clip ownership:** On a confirmed `AVAudioSession.InterruptionType.began`, Swift emits the existing `biblozooReadLifecycle` event with fixed `phase:"audioInterruptionBegan"` **before** `cancelAll(reason:"interrupted")`, even with no current `clips`. Genuine hardware route-loss/arrival `oldDeviceUnavailable`, `newDeviceAvailable`, `noSuitableRouteForCategory` produce `routeInterrupted`; media-services loss/reset produces `mediaServicesInterrupted`. Existing early `willResignActive` remains. **Do not** emit pause on unrelated route categories/override, a paused PiP, normal AVPlayer ended, or app foreground entry. The Swift notification handlers **never** activate/deactivate, mix, duck, start/restart output or request mic; they only notify and stop.
2. **One JS Read-wide interrupt owner:** `verse_games/shared/native-read-my-verse-output-n7f.js` handles exactly the four above named lifecycle phases. It revokes stale activation/cues/clip request IDs, emits **error rather than fake ended** to interrupted in-flight clips and invokes its existing `onAppInactive` activity callback even if `clips.size===0`. `read_my_verse.js` already has one activity-level `pauseReadForInterruption` that snapshots active scene/typing-intro/quiet-timer state, freezes CSS/cursor/timers, stops owned native audio and displays the shared Welcome Back overlay. This applies to **Keyboard, Typewriter, Tap Words in Order, Unscramble, Chunk Audio Matching, Balloons, Fish, Verse Crawl** through the same owner. Repeated lifecycle/clip events are idempotent and must not trigger completion, score, sound or hidden foreground replay.
3. **Truthful deliberate resume:** On the actual **Let's go!** touch, still synchronously call the existing `BibloZooNativeReadOutputController.activateFromGesture()` (same `.soloAmbient` session) to ask iOS to reclaim audio priority, **not** on foreground/return/OS `.ended`. In a quiet Keyboard/Typewriter/Order/Unscramble `kind:"ack"` recovery, the original code immediately hid the popup without awaiting the native session decision; now native-only quiet recovery retains Welcome Back until the **native claim returned `activated:true`**. A real OS denial leaves `Audio isn't ready yet. Try again!` and the same popup/Back route, with no new layout control. Animated quiet stages (no narration promise) also check native activation before clocks thaw. Playing narration still needs actual native position/ended as before; an activation ACK is **not** acoustic output proof and never awards a chunk or a Read game score. Original browser/PWA/Android immediate quiet ACK + Web tones remain unchanged.
4. **Preserved guardrails:** No new `setCategory`, `.mixWithOthers`, `.duckOthers`, `notifyOthersOnDeactivation` or direct Web Audio fallback in Audio Test; no extra microphone permission, capture DSP, sample upload or RAM recording change; no modified sounds/Wacky choices, animal profiles, Zoo score/rewards or UX/CSS. Owners of other native game and Flashcards audio remain independent.

It simulates genuine external-audio `.began` **while the app and WebKit are foreground and zero native clips are active**, verifies Welcome Back + frozen Keyboard/Typewriter/animated screens and retained progress, no stale tones, denied native activation retains popup/error, real next Let's go activation thaws, extra route/media/held-switch events idempotent, interrupt during true native playback emits error not ended, late activation after a second interruption cannot clear popup and Web/PWA adapter remains inert.
