## 1. Product and users

BibloZoo helps children memorize Bible verses through guided learning, practice games, Playground activities, Flashcards, Read My Verse, daily activities, and collectible BibloPets. A parent/family can use multiple **Zookeeper profiles** on one device. The application is primarily static HTML/CSS/JavaScript, also available as a web/PWA experience and packaged on iOS with Capacitor.

Progress and profiles are kept locally on the device. Backup export/import is an explicit user action. Verify the live [privacy policy](../privacy_policy.html) and native privacy manifest before making any claim about data collection, accounts, tracking, or release readiness.

## 2. Non-negotiable preservation rules

1. **Audio ownership is activity-specific; the iOS target is changing.** Current Web-era recovery rules and actual-clock probes remain in effect in `ios-prep` and web/PWA/Android. In the *experimental iOS native-only migration*, do **not** require a Web Audio clock, create Web/HTML sound output as recovery, or interpret a bridge `prepared`/`accepted` result as human-audible proof. Build native, owner-scoped playback/interruption verification instead. Retain legitimate interruption protections and the existing `.soloAmbient` policy unless a separately designed, iPhone-tested change is approved. Read [AUDIO-RECOVERY.md](AUDIO-RECOVERY.md), noting that its legacy Web flow is not the target architecture for the experiment.
2. **Do not silently lose child progress.** Preserve active verse, score, round, timers, recordings, Playground work, and saved profile data across interruptions, exits, and migration. Respect normal versus special Daily Zoo To-Do navigation.
3. **No accidental rewards.** Daily Questions, Daily Zoo To-Do, Feeding, rescue statistics, and developer simulations have distinct eligibility rules. Do not award completion twice or give achievements for simulated failures.
4. **Interruptions and cancellation are real lifecycle events.** Clean up listeners, timers, pointer capture, audio handles, and overlays; stale asynchronous callbacks must not revive a completed/exited activity.
5. **One experience, different owners.** Shared Welcome Back / Zoo Escape controls presentation and rescue stages; Learn, Feeding, games, Playground, Flashcards, and Read My Verse still own their audio, pause/resume, and exit logic. Screens that never needed a prompt should remain unchanged.
6. **Accessibility and offline are first-class.** Retain tap-to-rescue alongside dragging, reduced-motion behavior, screen-reader guidance, and the asset/service-worker path needed by standalone games. Native Capacitor and web/PWA loading are not identical.
7. **No silent release of developer tools.** The hidden whole-app Zoo Escape test harness has historically been enabled, as has Feeding's separate test path. Check their *current source flags* and disable or gate them for public release; do not infer they were already disabled.
8. **Native / privacy changes require special review.** Do not casually alter Capacitor packaging, AVAudioSession category/activation rules, backup format, privacy policy, or `PrivacyInfo.xcprivacy`.

## 4. Current behavior and important product decisions

- **Zoo Escape (72.1A–72.1D):** A failed Welcome Back audio-recovery attempt starts an escaped-pet rescue; a second failure can trigger ZOO BREAK with multiple pets; a final genuine failure exits safely to the title/home route. Pending native interruption is **deferred**, not counted as a failed attempt. The card remains playable without sound. The Zoo Escape developer menu tests failure/deferred cases without faking successful audio. Stage 3 rescue is not proof of restored audio—LOCK GATE still requires an activity-owned check.
- **Rescue achievements:** `BibloPets Rescued` and `Zoo Breaks Stopped` are per-Zookeeper; simulations must not increase them. The latter counts only after all Stage 3 animals are caught *and* real final-gate recovery succeeds. Stats belong in **Zookeeper Stats**, not as a persistent line beneath Zoo To-Do on the home screen. A genuine new achievement may trigger the one-time Zoo Hero home celebration.
- **Feeding (73–73.1):** Classic, Labyrinth, Melody, and Bounce use a two-step start: choose **Tilt** or **Drag**, then selected-method instructions and **Got It!**. The choice applies to that game session, including interruption recovery. Bounce re-serves do not reopen control choice. Collision notes and sizes have been tuned; Melody's visual contact should align with the scheduled musical note. Verify real iPhone behavior, especially motion permission and touch/tilt isolation.
- **Learn narration return gate ([PR #5](https://github.com/andydoane/biblozoo/pull/5), merged 2026-11-06):** Learn Listen/Chunks/Echo recovery now requires advancing HTML narration `currentTime` from the same source/attempt, not success of the unrelated UI Web Audio context. The 3.5-second bounded retry, interruption cleanup, and existing Zoo Escape owner callbacks remain. The final PR regression and web-build checks passed; physical iPhone verification has not been reported.
- **Verse Launch Game Menu pause ([PR #6](https://github.com/andydoane/biblozoo/pull/6), merged 2026-11-06; iPhone verification pending):** The word conveyor previously continued moving behind Game Menu. The fix stops and restarts it only when no menu/help/speed overlay or iOS Welcome Back owns pause, and freezes the asteroid bonus activity clock and delayed work behind menus. No audio-session or completion/reward changes. [Post-merge integration CI passed](https://github.com/andydoane/biblozoo/actions/runs/42313008623); owner physical-device acceptance has not been reported.

## 6. PR collaboration workflow (mandatory)

For **all app, game, native, documentation and regression work**, use feature branches and PRs. For the native-audio experiment, also follow the staged gates in [§10](#10-native-avfoundation-experiment-roadmap--living-experiment-only):

1. Re-read this handoff, then **refresh GitHub `ios-prep` HEAD**, open/merged PRs, issues, relevant source, `package.json`, and any available checks. Do not design from a stale chat or handoff.
2. Confirm the owner's latest requirement. Check whether their local edits have been **committed and pushed**; GitHub cannot see unpushed work. Normally **do not request a ZIP** when GitHub holds the correct source.
3. Create a short-lived feature branch from the current PR **target branch**—normally `ios-prep`, or `experiment/native-ios-audio` for the explicitly isolated native-audio workstream—never `main`. Keep changes focused, preserving the guardrails above.
4. Implement the code, focused regression tests, and **handoff update in the same branch/PR**. Update [TESTING.md](TESTING.md) or [AUDIO-RECOVERY.md](AUDIO-RECOVERY.md) when their contracts change.
5. Run what the environment actually supports; state commands, exact result and limitations truthfully. On GitHub, review any applicable Actions checks on the **final PR commit**, not an earlier one.
6. Open a PR targeting **`ios-prep` normally**, or **`experiment/native-ios-audio`** for the native-audio experiment. Prefer a draft while checks are incomplete; include the summary, risks, verification evidence, and a short iPhone checklist. **Leave it unmerged.** The owner reviews and merges.
7. After merge, the owner switches in GitHub Desktop to **the PR's target branch/worktree**, pulls, builds/syncs, and tests on a physical iPhone. If the device test fails, open a **follow-up PR** to that branch. An automated green check is not a claim of physical-device acceptance. Do not install experimental code using the original iPhone bundle identifier.
8. No direct pushes to `ios-prep` or `main`, PR merges, or releases without the owner's explicit instruction. Branches for each task, PR review, and owner-controlled merge are the default.

## 7. Mandatory handoff maintenance (self-perpetuating)

**Every future PR must update this file.** A future assistant reading this handoff must carry this instruction forward, not treat it as optional housekeeping:

- Include the handoff in the PR's changed files and tick the corresponding [PR template](../.github/pull_request_template.md) box. If unable to update it, disclose the reason in the PR and flag it as unfinished for the owner; **do not silently skip maintenance**.
- Document only durable decisions and actionable open work. Correct stale content rather than preserving it as authority. The source, current tests and owner's latest directions always win.
- **At the end of each PR**, tell the owner what this document now says, what was actually verified, and what remains for the owner to test.

**Post-merge device findings are a second handoff trigger.** A PR can correctly document an open/pending owner gate at submission time, but once the owner merges and tests it, the next PR (or a docs-only correction if no code PR is appropriate) must record the **actual merge SHA, final CI status, owner-reported pass/fail details, outstanding exceptions, and next actionable PR**. Never leave a just-merged PR labeled “current/unmerged” as the newest status. If a known issue appears across games, record it as a reproducible observation without assigning a speculative root cause.

This policy is deliberately written *inside* the handoff so a completely new conversation can continue maintaining it without the old chat.

### Owner-approved architectural decision (supersedes the old hybrid Stage D–H roadmap)

- **Destination: iOS playback/output is native AVFoundation only.** BibloZoo stays a JavaScript/Capacitor application for screen UI, game logic, state, art, animation, and rewards. Do not reinterpret this as a full Swift game rewrite. Stable `ios-prep` is unchanged unless the owner later authorizes a separate integration PR.
- **In the isolated `.audiotest` iOS app, no silent fallback to Web Audio, HTMLAudioElement, or WebKit media output.** Once the native-only migration's global isolation gate exists, *every sound audible on that experimental iOS app must come through the native backend*. Preserve the old browser/PWA/Android implementations **for those platforms only**. Use original/stable BibloZoo separately for Web comparison, not covert playback inside the native experiment.
- **Temporary missing iOS sound is acceptable research debt, not release success.** Do not use Web sound to camouflage a missing native feature, and do not block progress solely because native tones, narration, or advanced effects have not yet migrated. Surface missing/native-failed state explicitly; preserve input, game progress, accessibility, exit, mute, rewards, and recording data. Before production integration all required output/recording flows must be covered or have an explicit reviewed policy.
- **`Got It!` should be the real user gesture for the selected native activity.** Remove the old Web Audio resume/clock precondition from the experimental iOS start/return path, and replace it with bounded native prepare/activation and appropriate native player/session evidence. Do not infer speaker audibility from `prepareToPlay`, `play()`, `isPlaying`, or `getDebugState`. A real interruption still needs a safe, explicit user action; do not auto-play on foreground.
- **Zoo Escape and ZOO BREAK are future FUN surprises, not audio-repair tools.** The existing Web-era failure-driven rescue behavior stays intact in stable/web paths during migration; the experiment can decouple it from audio failure. Design random, cooldown-aware opportunities on eligible `Got It!` taps only **after** dependable native playback and the new start lifecycle are established. No random rescue events in N1. See §10.
- **Protect each Zookeeper's data and gameplay.** No double completions, repeated rewards, lost verse/round/timer, interrupted recording replay, or simulated rescue credit. Experimental and stable iOS bundle IDs and storage remain separate; never overwrite the original installed app.
- **Separate output from capture/DSP.** Avoid WebKit-produced *audible output* on experimental iOS; microphone recording, Flashcards metering/Wacky Replay, and Read My Verse recording have different semantics and need an explicit, later native-input/DSP decision. Do not silently call the entire app fully native while those paths still use browser media APIs.

## 10. Native-only iOS architecture and incremental migration roadmap — owner-approved direction

**Purpose.** Replace the current mix of WebKit sound rendering, Web Audio recovery, and narrow native output with a single intentional AVFoundation sound system for the *experimental iOS app*. This incorporates the November 6 `Reliable iOS Audio for BibloZoo` assessment's Swift-plugin, native player, instrumentation and phased migration analysis, but **supersedes its Web fallback / hybrid pilot preference for this experiment**, per the owner's explicit decision on November 7. This is an engineering hypothesis with required physical-device validation, not a claim that AVFoundation prevents all interruptions.

**Scope:** experiments/feature PRs target **`experiment/native-ios-audio`**, branching from its current HEAD, not `main` or `ios-prep`; leave PRs for owner review/merge. Preserve the separate `com.andydoane.biblozoo.audiotest` identity and the original BibloZoo installation. Update this handoff in every PR. Update [TESTING.md](TESTING.md) and [AUDIO-RECOVERY.md](AUDIO-RECOVERY.md) when actual code contracts change, including replacing old hybrid guidance with scoped native-only steps. Never delete working browser/PWA/Android audio code without explicit cross-platform review.

### Target architecture / boundaries

`JavaScript game/activity owners → one backend-neutral sound API → native Capacitor bridge → AVFoundation output (AVAudioPlayer for clips, AVAudioEngine when synthesized/polyphonic/timed sound warrants it) → iOS device route.` No independent Web/HTML output path should run inside the final experimental iOS configuration. Keep an allowlisted sound manifest, per-activity/request IDs and generations, and distinct `prepared` / `accepted` / `progressing` / **human heard** observations; never claim a native status API proves speaker output.

Native audio-session policy should have **one deliberate coordinator** for activation/interruption/route/media reset, not unrelated plugins racing to set category/active state. Begin by preserving `.soloAmbient`, silent-switch/foreground-only semantics, microphone privacy and the existing no-auto-replay rule. A category/activation redesign may be justified later **only** by a focused review and physical iPhone evidence. Stale `.began` notifications and genuine current interruptions must be distinguishable; never clear an actual pending interruption just to make a test appear green.

### Standing release and evidence rules

1. **No hidden fallback:** If the experimental iOS branch produces sound, it must be traceable to a native sound ID and plugin call. Web/HTML paths are preserved for web/PWA/Android, not invoked to “save” native iOS output. Use the original installed BibloZoo app for any Web baseline.
2. **No false pass:** Silence is allowed **during development**, but is recorded as unmigrated/failed, never `audible native success`. Node mocks, successful `AVAudioPlayer.play()`, advancing clocks and Swift compilation are distinct from a human hearing the actual effect.
3. **Gameplay state is sacrosanct:** Preserve pet progress, verse, timers, recording/mic content, local backups, daily reward eligibility and accessibility. Interruption and cancellation must invalidate stale audio/game callbacks.
4. **Session safety and privacy:** No forced audio category change, recording activation, background entitlement, profile/verse/audio-content telemetry, or spontaneous resumed playback without dedicated review and device testing.
5. **PR discipline:** Each slice is a short-lived branch against `experiment/native-ios-audio`, with focused tests, mandatory update to this handoff (including stage status/date/commit/device evidence), relevant testing/audio docs, owner review and merge. Source/CI, Xcode build, and physical audible output always have separate statuses. Review hidden developer test menus before any public release.
