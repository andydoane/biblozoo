**Cause of misleading label (verified source):** In Native-only Feeding, `setFeedingResumeStatus` forwarded `retry: !!message` to the shared Welcome Back action even when `feedResumePending=true` and the message was only “Preparing native sounds…”. The noteIndex is a strictly bounded integer 0–5 matching existing six original Web Classic pitches, with original **55ms** throttle and no same-note repeat. On actual Got It!/Resume preflight the existing Swift worker generates six short **105ms native mono sine PCM buffers** and prewarms **four** peg player-node voices on the existing `AVAudioEngine`, while prewarming **two** independent voices for each star/chomp sample. At collision only a preexisting node and buffer are chosen; no Web/HTML oscillator, MP3 decode, node/engine startup, AVAudioSession call, or unbounded allocation. When the tiny voice pool wraps, reusing that node may truncate its prior sound; overlap is intentionally capped. Native-only other Feeding modes remain unmigrated and silent for these tones; old Web/PWA/Android keeps its exact oscillator behavior.

**Safety and diagnostics:** The experiment retains `.soloAmbient`, explicit native gesture gating, genuine interruption and route/media reset cancellation, old voice teardown/no automatic replay, the static N1 WebKit output guard, user data, microphone/recording privacy, scores and Back. An engine failure leaves a visible native refusal, never Web fallback. Existing **Copy Audio Timing Report** stays user-tapped and local; new native peg rows use `backend=avengine-tone`. A `scheduled` row only times native buffer scheduling, **not actual audible sound**. If notes are too loud, late, clipped, silent or the Swift graph fails, report real iPhone behavior and optional copied log; do not claim success from GitHub Node tests alone.

## N3a — predecoded native PCM effects, no Web fallback (PR #24 merged; owner iPhone accepted PCM timing)

**Merged N2.2 [PR #23](https://github.com/andydoane/biblozoo/pull/23), owner physical-iPhone evidence (2026-11-07):** Two user-copied native timing reports contained 27 Classic Feeding events, of which **13 took >=120ms** from collision to native dispatch. Of these delayed events, **12 were mostly `AVAudioPlayer.play()` itself taking ~392–744ms**; the thirteenth waited **457ms in the serial queue** behind a 459ms star playback call. Collision→JS request and JS→Swift bridge were generally 0–3ms. The owner still heard every star/chomp and gameplay stayed visually smooth. **Audible onset was inconsistent**—sometimes chomp felt immediate, other times delayed. The Native timing report does **not** measure hardware/speaker onset or explain exactly what AVAudioPlayer did internally. Task switching was not necessary for slow play rows; the owner has not explicitly confirmed that task-switch → Resume succeeds since N2.1.

**[PR #24](https://github.com/andydoane/biblozoo/pull/24) N3a**, branch `experiment/n3-predecoded-native-feeding-effects`, is an isolated **native output-engine experiment**, not a production/stable fix yet. The native Swift sound plugin continues to own the sole `AVAudioSession` output activation path and uses `.soloAmbient` with existing genuine-interruption gating. `feed-star` and `feed-chomp` are decoded at the explicit Got It!/Resume/DEV preload gesture using `AVAudioFile` and bounded `AVAudioPCMBuffer`; the worker builds/starts/warm-prepares a single `AVAudioEngine` and two `AVAudioPlayerNode`s without queueing an audible clip. When a collision later calls the unchanged `BibloZooNativeSound.play`, Swift **schedules the already-decoded PCM** on the right native player node using `scheduleBuffer(...options:[.interrupts])`; it does not decode MP3, start the engine, or call `AVAudioPlayer.play()` in that hot path. Both new sounds remain **100% native**, with no Web/HTML fallback if a PCM buffer/engine fails. `pilot-unlock` remains the independent native `AVAudioPlayer` DEV baseline.

**Lifecycle:** Backgrounding, real interruptions, route changes or media-services reset invalidates the current worker playback epoch and disposes both PCM nodes/buffers, the native engine and any pilot player. A new Got It!/Resume gesture may preload again only when Swift session eligibility allows it. `stop` on an effect tears down the warm effect graph. No automatic sound on foreground, no category/mode/mic/background entitlement changes, no Web recovery or Zoo Escape audio repair; scores/rounds/recordings/Back must remain intact. The engine is running silently during a native active round to avoid a costly hardware start on each effect, and is torn down on exit/stop/background. Same-ID rapid retriggers interrupt their own previous clip; polyphonic pools are a separate future N3 slice.

**Diagnostics:** The user-friendly DEV **Copy Audio Timing Report** remains local (80 in-memory events, manually copied through Swift UIPasteboard), now appends a `backend` field per row: `avengine-pcm` for effects, `avfoundation-player` for DEV pet-unlock. `worker call` now means the native **PCM buffer-scheduling operation** or, for legacy pilot, the original `AVAudioPlayer.play()` call. `collision->native dispatch` still ends at the software call returning, not the sound reaching the speaker. The owner should listen and send a new report after PR #24 is merged and built, rather than assume shorter native call times prove audio quality.

**Validation boundaries:** GitHub Node/static/VM checks and production web build are distinct from **Swift/Xcode compile** (not available in Linux CI) and real **iPhone audible timing, game smoothness, and task-switch Resume** (all pending N3a acceptance). On failure preserve the exact native reason (`pcm-decode-or-engine-start-failed`, `pcm-not-preloaded`, `effect-too-large-or-empty`) instead of re-enabling WebKit media. No new peg beeps, narration, recording migration or Zoo surprise behavior in this PR. Further N3 covers voice pools/native tones, later N4–N7 other media and N8 child-friendly independent random Zoo Escape. See [N3a native PCM technical and iPhone guide](N3-NATIVE-PCM-EFFECTS.md), [TESTING.md](TESTING.md), [living handoff](PROJECT-HANDOFF.md).

**Native event history:** `getDebugState()` now includes bounded last-28 `recentEvents` records with monotonic sequence, elapsed time, app state, foreground epoch, pending boolean and numeric interruption code. The DEV Inspect button shows last-eight-event shorthand and activation attempt/result counters without playing sound. It never records user or recording content and makes **no activation call**. Native `.began` with `AVAudioSessionInterruptionWasSuspendedKey=true` is historical and does not itself create a new pending latch; unrelated older pending remains protected. `.ended` clears pending eligibility without auto-resume. Route changes and media resets dispose old players, and resets require a new explicit gesture; a changed category after reset remains a reported limitation requiring review, **not** permission to force a category during microphone capture.

## Why this subsystem exists

iOS / WKWebView app switches and interruptions may leave Web Audio playback stalled even when a JavaScript object says its `AudioContext` is running. BibloZoo must distinguish genuinely advancing audio from merely available or resumed APIs. A failed recovery can trigger the child-friendly Zoo Escape minigame without changing the underlying activity's audio truth.

The shared recovery UI is **not** an audio engine. It must remain fully playable without sound.

## Non-negotiable behavior

1. **Only a real recovery probe can establish success.** A successful note, a resumed `AudioContext` state, a native diagnostic snapshot, a tap, animation completion, or a simulated developer result is not sufficient. The owner checks that its actual audio/playback clock advances.
2. **No automatic native activation from foreground or decorative sounds.** The bounded native path is considered only after observed stalled Web Audio, through the existing guarded coordinator. Do not create/resume/replace a context just to play Zoo Escape sounds.
3. **Preserve the existing native category and interruption policy.** The app intentionally retains **`AVAudioSessionCategorySoloAmbient`**; do not change category, mode, or audio-session handling without a deliberate, device-tested design review. Native diagnostics must remain observational; the existing bounded reactivation must not be expanded into a generic auto-recovery loop.
4. **Keep a pending interruption distinct from a failed attempt.** If the native signal still says interruption began / recovery deferred, preserve the current LOCK GATE stage and allow another deliberate attempt. Never escalate Zoo Escape just because iOS has not finished the interruption.
5. **Activity-owned callbacks.** The shared Welcome Back/Zoo Escape controller may display stages and request a recovery, but the owner still pauses physics/audio, checks its own playback, resumes on verified success, and cleans up or navigates on exit. In Verse Launch, local Game Menu, Help and Speed Menu pauses share one pause-aware activity clock with task-switch handling: closing a menu must not resume clock time while Welcome Back still owns the pause, or advance the conveyor/bonus timer behind overlays. This local menu behavior does **not** change the audio recovery gate.
6. **Real gesture and bounded deadlines.** On LOCK GATE, the activity-owned recovery callback must run in the real user gesture; avoid introducing deferred synthetic clicks that break iOS unlock behavior. Timeouts and stale-generation guards prevent loops or delayed state changes after exit.
7. **Respect quiet or microphone activities.** A quiet Daily return may be acknowledgement-only; do not invent an audio test. Learn's Listen/Chunks/Echo recovery must verify advancement of its actual HTML narration position; an independent app UI Web Audio failure must not veto narration. A fulfilled `HTMLMediaElement.play()` alone is insufficient. Flashcards / Read My Verse must never spontaneously begin recording or overwrite a partially completed take.
8. **Do not break gameplay on failure.** Zoo Escape may be silent, and rescue stages must still be interactive. On final failure or early exit, execute the owner cleanup and correct route (including special Daily To-Do returns). Preserve score/progress and avoid duplicate rewards.
9. **Do not credit developer simulations.** The hidden testing harness can force failures or deferred outcomes, but the real recovery owner is still required for success. Simulated rescues must not increase persistent per-Zookeeper rescue statistics.

## Zoo Escape lifecycle in brief

| Phase | Expected action |
| --- | --- |
| Return after an interruption | Show Welcome Back and pause activity-owned gameplay |
| Recovery verified | Dismiss safely and resume same activity/progress |
| First genuine failure | Stage 2: one named pet escapes; rescue it; LOCK GATE retries |
| Second genuine failure | Stage 3: ZOO BREAK, several distinct pets; catch all; final LOCK GATE |
| Recovery still pending | **No additional failed attempt**; keep the gate at its current stage |
| Verified final-gate success | Activity resumes; a genuinely stopped Zoo Break can earn credit |
| Final verified failure | Fade and execute a safe, activity-owned exit to home/title where appropriate |
| App switched while animals loose | Suspend and resume the **same** rescue stage and caught-pet state; no duplicated pets |

Appearance details can evolve; the audio and state boundaries above must not.

- Foreground/background return with active sound; successful recovery must resume *the same round*.

## Experimental AVFoundation output smoke test (PR B)

On the separate `experiment/native-ios-audio` branch only, PR B proposes a user-tapped `BibloZooNativeSound` `AVAudioPlayer` test. It does not attempt Web Audio recovery, set session category/mode/active state, replace a narration clock, create a UI-audio success gate, or automatically resume. Swift requires foreground + the existing `.soloAmbient` category, accepts only `pilot-unlock`, rejects invalid/nonfinite volume, and stops/forgets playback on inactivity, interruptions, route changes or media resets. The JS test button times out rather than waiting forever, cancels stale playback on background and never runs in browsers/PWA.

A successful `preload` or `play` bridge result means the native request was prepared/accepted, **not** that sound reached the speaker.
